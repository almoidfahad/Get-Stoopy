# COD multi-delivery accounting safety boundary

The current test-foundation finance path creates a COD collection for **the full order amount on every completed delivery**, while each delivery belongs to one vendor suborder. For an order split across stores, this can duplicate the order amount in rider custody and the COD clearing ledger. That is a code/design risk, not evidence that a real collection was made. The current order amount is product subtotal only, not an approved customer final total; migration `0041` also requires that same order amount for each collection. Substituting a suborder subtotal would not solve allocation of customer delivery, tax, discounts, split delivery failures or database/settlement constraints.

Until a reviewed per-delivery COD allocation and reconciliation design exists, the application refuses **new dispatch runs, new offers, acceptance of open offers, pickup confirmations and completion** of COD deliveries unless the order has exactly one suborder, it is the requested suborder, its currency and subtotal equal the order amount and currency, and its pricing scope is the legacy `PRODUCT_SUBTOTAL_ONLY`. The same check runs independently at the finance journal-writing entry point. These checks also apply to older runs, offers and assignments. Refusals return `409 COD_ALLOCATION_REQUIRED` before the corresponding state changes or financial writes. Idempotent replays of prior actions remain readable, and riders can still reject open offers; expiry is not blocked. Existing runs, offers, assignments, physical handoffs or previously posted collections are not reversed, and already confirmed pickups or OTP paths are not stopped. Operations must not dispatch or collect money on unreviewed existing orders; inspect/reconcile them independently. An actual physical pickup or recipient handoff cannot be undone by a failed request.

This is a narrow application-level safeguard, not a database invariant. Privileged SQL or other paths can bypass it; it assumes supported order creation completed before dispatch and does not serialize arbitrary privileged suborder writers. It does not repair historic data, validate that cash was actually collected, authorize a fee, or make even single-store COD production-ready. COD order creation remains hard-disabled outside test, as documented in `docs/162`; existing read/cancel behavior is unchanged. Do not set test mode against real data. No migrations, hosted data, workers or deployment are changed.

Unit tests cover zero/multiple/wrong suborders, mismatched amount/currency/scope, denial before offer, acceptance, pickup, completion and finance writes, plus offer rejection and replay/ownership behavior. A disposable integration test creates an actual synthetic two-store COD order, verifies both dispatch attempts fail, checks the same guard against actual Prisma records and confirms no dispatch, delivery or collection rows before cancelling/restocking. A separate disposable integration test uses a temporary test-only mock to construct simulated pre-guard runs, offers and assignments, then restores the guard and verifies each next step is refused without a corresponding state transition. Existing disposable dispatch integration tests continue to exercise the legacy single-store test path. The separate multi-delivery OTP rate-limit test uses synthetic verified sandbox payment, so it continues testing recipient concurrency without bypassing the COD dispatch guard. These tests do not demonstrate a multi-delivery COD fulfillment or real-world COD reconciliation.

For future COD-only checkout, obtain approved customer pricing/tax/discount rules; build a durable immutable allocation per delivery (including rounding, failed/partial deliveries, cancellation and return treatment); bind it to an authoritative recipient, quote, order, assignment and proof; replace the DB collection and deferred invariants and settlement assumptions in a reviewed migration; add concurrency/idempotency, journal/deposit and reconciliation tests; assess existing data, recovery and operational controls; and only then separately review launch. Rider compensation must not be substituted for customer delivery charges. Online payments are not enabled by this work.
