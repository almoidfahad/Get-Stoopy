# Test-only recipient draft retention worker

The encrypted test-only recipient draft expires logically after 24 hours. This increment adds a bounded worker tick which, when enabled and running, clears the current envelope and expiry of due drafts and increments the existing tombstone version. It writes a metadata-only SYSTEM audit and reports only counts or a generic failure in worker logs. It does not need the encryption key and never decrypts data.

The worker is disabled by default. `CHECKOUT_DRAFT_RETENTION_ENABLED=true` requires both `NODE_ENV=test` and a privileged database URL; polling and batch sizes are bounded. It is intended only for a disposable isolated test database. The HTTP draft feature remains hard-disabled outside test, is not bound to checkout and must not receive real user data. There is no hosted migration, configuration change or deployment in this increment.

The tick locks cart rows first, in the same order as draft save and clear, skips carts currently locked by a buyer or another worker, and rechecks expiry during the update. This prevents a worker from overwriting a newly refreshed draft. The draft update and its audit share one transaction; if either fails the entire batch rolls back. Optimistic versions remain monotonic, so an old writer cannot revive an expired tombstone. The privileged worker temporarily sets transaction-local buyer context for the database's owner guard. Direct privileged database writers can bypass the cart-first convention and must not be treated as covered.

Disposable PostgreSQL tests cover a locked cart, injected audit failure and rollback, idempotent repeated ticks, stale-version rejection, a waiting buyer refresh versus a worker, concurrent bounded workers, an unexpired draft, audit counts, configuration gating and sensitive-data-free worker logs. Operational scheduling and exact purge latency are not guaranteed when the worker is disabled, down or backlogged.

**Clearing a current row is not secure deletion**: PostgreSQL old tuples, WAL, replicas, backups and external logs may retain previous encrypted bytes. Backup/replica retention, key lifecycle and rotation, key loss recovery, privacy/legal review, monitoring and production-safe observability remain unresolved. The draft's finite integer version can eventually exhaust and cause the tick to fail closed; monitoring and an operational recovery procedure are needed before any production use. A real customer checkout also needs an authoritative, transactionally bound recipient/zone snapshot, fees/tax and complete total.
