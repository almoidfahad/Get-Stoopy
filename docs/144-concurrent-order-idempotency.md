# Concurrent order-creation idempotency

Order creation previously looked up `(buyerId, commandKey)` before taking the quote lock. Two concurrent requests could both miss the lookup: identical retries against one quote then returned a consumed-quote conflict instead of replaying the order, while the same key sent against different quotes could race the unique constraint and surface an internal error. Existing unique indexes prevent duplicate orders, but they do not provide correct retry semantics.

A transaction-scoped advisory lock now serializes each buyer's exact command key before the idempotency lookup. The buyer ID is normalized for the lock key; key case remains significant. The quote row lock and existing ownership, version, expiry, COD and database checks remain unchanged. Reusing a committed key with changed payload gives `ORDER_IDEMPOTENCY_CONFLICT`, and a different key against the same consumed quote still gives `ORDER_QUOTE_NOT_CONSUMABLE`. Lock hashing coordinates requests only and does not authorize them; rare hash collisions only serialize unrelated commands.

Disposable PostgreSQL integration tests hold a quote row until both HTTP requests are waiting. They exercise an identical retry, reuse of a key on a different quote, and separate keys on the same quote. They assert one order, one consumption movement, one audit and outbox event, the expected stock balance and the untouched second quote. No schema migration or production data change is included. These tests do not implement real payment, delivery fees, end-to-end checkout, hosted deployment or generic idempotency for other commands.
