# Vendor orders workspace layout

The vendor dashboard now links to `/vendor/orders`, a static, responsive layout preview with a labeled, horizontally scrollable order table and an unavailable-record state. It explicitly distinguishes unavailable records from an empty store. No sample orders, totals, customer data or live status claims are shown. The readiness guidance reflects the existing development implementation: vendor acceptance (with estimate) or rejection (with reason), preparation, and manual ready confirmation. It is not a full lifecycle or an order status indicator; later delivery, cancellation and exception states are not represented as a linear sequence.

The page is public because it contains no store or order data and grants no vendor permission. It makes no API calls and cannot accept, reject, prepare, or mark an order ready. Search, filters, details, store selection and actions are not implemented. A real interface must separately enforce the backend's store-scoped membership and read/write permissions, minimize customer data, and handle CSRF, explicit manual ready, estimate/rejection validation, idempotency keys, version conflicts, payment/store eligibility and errors. See `docs/35-vendor-suborder-fulfillment-readiness.md` for the development API; do not infer that it is connected or deployed.

Server-rendered tests check the unavailable messaging, accessible table structure, stage explanations and absence of misleading actions. They do not verify a real browser, assistive technology, visual fidelity, live authorization or order handling. The supplied vendor reference includes recent orders but not a dedicated orders page, so this layout is an interpretation awaiting design review. No production deployment, payment or database settings were changed.
