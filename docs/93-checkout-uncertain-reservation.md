# Checkout reservation retry safety

The checkout panel now keeps the complete in-memory reservation attempt (destination, cart version and attempt ID) when the result is uncertain, including network errors and server errors. A retry sends that exact payload even if a server refresh changes the cart version or city list. The city cannot be changed while the result is uncertain. The message warns that stock may already be held and offers an identical retry or a checkout reload to check for a quote. A recovered quote can be released, but does not clear the pending attempt because it may belong to another request; certain explicit API rejections on the first response, such as a cart-version conflict, end that attempt so a later request can use a fresh key and updated inputs. A rejection after an uncertain response does not establish the fate of the original request, which may still be in flight. Unknown errors and sign-in failures do not establish that a previous request failed; they retain the attempt. The backend remains authoritative for idempotency, stock and conflicts.

The attempt is held only for the lifetime of the mounted panel, not persisted across reloads or browser tabs. Reload recovery uses the existing active-quote lookup; a missing quote on reload cannot prove that an earlier request still in flight will not later succeed. Multiple tabs, sessions, network races and cart changes require live concurrent integration testing before claiming end-to-end safety. Tests in this increment mock network and router behavior; no live service, database, payment, order placement or production deployment was changed.
