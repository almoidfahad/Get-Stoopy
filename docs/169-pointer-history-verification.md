# Pointer history: local verification and CI limitation

GitHub Actions PR run `43050634098` for `abaa2ae` originally did not start because of a billing/spending-limit issue. That historical blocker was resolved: PR run [43163598927](https://github.com/almoidfahad/Get-Stoopy/actions/runs/43163598927), attempt 2, passed both validate and the PostgreSQL/PostGIS/Redis integration suite on commit `df1822d`. This verifies the tests in that CI environment, not compatibility with any hosted database.

As supplemental checks only, the local unit/component suite passed 1,095 tests, API TypeScript build and typecheck passed, and Prisma's schema validator accepted the updated schema (a deliberately invalid control was rejected). A temporary PGlite/PostGIS instance applied the exact 0075–0077 migrations to a minimal synthetic schema and exercised pointer change history, append-only guard, failure rollback, application-role denial and the existing-pointer upgrade precondition. Separately, an isolated native PostgreSQL 16.13 instance with a minimal synthetic pointer schema applied the exact 0077 migration. Two real connections demonstrated an observed row-lock wait and rejection of a stale concurrent pointer change; history recording, direct-write rejection, failed-history rollback, role denial and upgrade precondition were also checked. The native test used a simplified pointer guard, not PostGIS, and neither temporary setup is equivalent to running the repository's full integration suite. The local database used a private Unix socket, no hosted service or real data, and was stopped afterwards.

The repository integration race test verifies actual database blocking using `pg_blocking_pids` before allowing the first transaction to commit; the upgrade-precondition test submits the full migration rather than an extracted prefix. Those integration tests passed in the CI run above. No hosted migration, checkout activation or deployment was performed.
