# Request-log route templates

The API request-context middleware previously logged `req.path`. Although query strings were excluded, a caller could place recipient information, tokens, or other private text in an invalid URL path before a UUID or other route parameter was validated. The request log would record that text even for an authentication or validation failure.

The application request log now uses the server-registered route template from Express, such as `/api/v1/commerce/carts/:cartId/recipient-draft`, instead of the request URL. It never concatenates `baseUrl`, `path`, `originalUrl`, request bodies or queries. Missing, non-string, oversized or unexpectedly formatted route definitions are labeled `[unmatched]`. This affects request logging across the API, so dashboards that grouped by literal paths or IDs must group by route template instead. It is intentionally lossy; diagnostics can still use the request ID, method, status and duration.

Automated tests exercise valid routes, invalid parameter values, unauthenticated requests and unknown paths with synthetic sensitive markers, checking the log contains templates rather than those markers or cart IDs. Request ID handling and early middleware ordering were subsequently hardened; see docs/161. This change does not sanitize separate application/exception logs or third-party CDN, reverse-proxy, web-server, tracing and database logs. Those need independent configuration and privacy review before real customer recipient data is used. No hosted configuration, deployment, checkout activation or database changes are included.
