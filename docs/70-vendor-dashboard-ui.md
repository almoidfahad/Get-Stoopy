# Vendor dashboard UI foundation

This first vendor dashboard increment is a responsive **layout only** at `/vendor`, inspired by `references/file_000000001fd08210b38f6b50c3a01087.png`: dark sidebar, vendor workspace header, red welcome panel, overview cards and reporting panels. It intentionally omits screenshot names, values, charts, support claims, store selectors and buttons for unimplemented workflows. The unavailable module names are plain non-interactive text, not dead links. This is not the complete vendor portal or an approved pixel match.

The page checks the existing `/auth/me` response and distinguishes signed-out, unavailable, no active vendor membership and membership-present states. It does not display membership IDs, session tokens or CSRF tokens. The layout and unavailable placeholders are visible regardless of session because they contain no vendor-specific information. A membership indicator is informational only and is **not authorization**: future real vendor data, store selection and every vendor action must be independently authorized by backend permission and vendor/store scope. No real dashboard aggregates, orders, catalog management, earnings, settlement, KYC state or reports are connected in this UI increment. Existing vendor APIs are not represented as connected by this dashboard.

Server-rendered tests cover the session states, malformed responses, unavailable metrics, missing feature links and absence of sensitive fields. They mock the session endpoint and do not prove live authentication, backend authorization, real data isolation, browser interaction, mobile visuals or accessibility. Vercel preview has no configured backend and should show the access-unavailable state. Those checks and the remaining vendor, rider and scoped admin experiences still need implementation and review.
