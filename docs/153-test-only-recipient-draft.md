# Test-only encrypted pre-order recipient draft

This increment adds an experimental buyer-owned draft to the API and migration `0074_checkout_recipient_draft`. The feature is **hard disabled outside `NODE_ENV=test`**. It is not connected to the web checkout, quote, order, delivery or payment. Do not use real customer data.

A save validates recipient/destination through the preview endpoint, rechecks the buyer-owned cart/version while holding the cart lock, and stores contact, address, coordinates, zone/boundary and cart-version in an AES-256-GCM envelope using the separate `CHECKOUT_RECIPIENT_DRAFT_KEY`. The plaintext is not stored in the new row. An authorized buyer can read their own unexpired draft with `Cache-Control: no-store` or clear it. The API response explicitly says coverage is not guaranteed and the draft is not quote-bound: coverage may change between the preview and save, and quote creation does not consume the draft.

The per-cart draft has a monotonic optimistic version. A cleared row becomes a null-envelope tombstone rather than resetting its version, preventing a stale create from silently replacing a newer draft. The cart row serializes save/clear commands and cart mutations. Same-version simultaneous writes result in one success and one conflict. Database RLS and grants deny runtime access; a trigger requires the current buyer for privileged inserts/updates and blocks direct deletes. Save and clear produce metadata-only audits; contact, address and coordinates are not placed in audit or outbox.

At this increment, the 24-hour expiry was **logical only**: expired data was hidden from API reads, but encrypted bytes remained until explicitly cleared. The subsequent test-only worker in `docs/154-recipient-draft-retention.md` can clear expired current rows when enabled and running. Clearing sets the current envelope to null; it does not securely erase PostgreSQL old row versions, WAL, replicas or backups. Key rotation and key-loss handling, backup/replica retention, infrastructure log redaction, privacy/legal review and operational monitoring remain unfinished. Clear remains available in test mode without the encryption key; recovery without the key is not possible. Production enablement is deliberately blocked until these gaps are resolved. No hosted migration was applied.

Disposable PostGIS integration tests cover disabled environments/missing key, owner and CSRF checks, encrypted at-rest bytes, direct runtime access denial, database owner guard, read/clear, stale-version and forced overlapping updates, tombstone replay protection, expiry, and metadata-only audit. This is not evidence of hosted privacy compliance or an end-to-end checkout.
