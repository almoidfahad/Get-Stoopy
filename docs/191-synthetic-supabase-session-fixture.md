# Synthetic identity-to-session rehearsal (not a login)

This is an isolated test fixture under `tests/integration`, not an API route or a production authentication implementation. It accepts only a reserved `.example.test` issuer, supplied local public asymmetric keys, `NODE_ENV=test` and an explicit test environment argument. No hosted project, user, token, network key discovery, migration, credential or provider setting is used. Those checks reduce accidental misuse, but are not a guarantee that the database supplied to the helper is disposable: **only use it with synthetic data on an independently verified disposable database.**

The fixture verifies a synthetic JWT with the unwired draft verifier, locks an already-linked `supabase-fixture` identity and local user within one database transaction, rejects unknown or inactive users, and creates a local opaque session with a token hash and the local authorization version. It caps both absolute and initial idle expiry at the synthetic JWT expiry; no provider token or profile metadata is saved. It does not create users, link identities, grant roles or treat provider metadata as marketplace authorization. The existing session resolver still determines local permissions and eligibility. The transaction is a candidate for experimentation only, not a reviewed production concurrency design.

Unit tests exercise the environment gate, policy and key restrictions, expired/wrong-issuer/wrong-signature tokens, unknown/inactive identity, local session attributes and expiry after lock wait. A disposable PostGIS integration test additionally exercises a synthetic pre-linked user, the existing `/auth/me` and logout endpoints, empty local permissions despite hostile metadata, token-hash storage and the inactivity gate. Run it through the repository's disposable CI integration job; never supply a hosted or valuable database to the integration suite. Unit mocks do not prove database rollback or locking, and the integration case does not prove concurrent revocation semantics.

## Remaining safety gates

This does **not** check live Supabase token format, key rotation, provider session/user revocation or status, account linking/provisioning, CSRF/login callback design, shared-project RLS/grants, MFA assurance mapping, rate limiting, audit logging, secrets handling, or compatibility with the existing editorial app. Provider revocation can precede JWT expiry. No auth redirect or real identity flow is changed. These and the previously documented schema isolation and COD ledger decisions must be designed and reviewed before any production use. COD remains disabled. See `188-supabase-free-plan-cod-audit.md`, `189-shared-project-local-rehearsal.md`, and `190-supabase-auth-token-boundary-draft.md`.
