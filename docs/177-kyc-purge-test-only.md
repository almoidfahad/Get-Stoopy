# KYC object purge is test-only

The KYC retention worker previously deleted external objects inside a PostgreSQL transaction. That is not an atomic operation: if one object is deleted and a later deletion, database write, commit or process fails, rolling back PostgreSQL does **not** restore the already-deleted object. A later legal hold can then encounter missing evidence even though the deletion request or storage metadata still appears unpurged. The previously documented database rollback/retry behavior is not a guarantee that external evidence remains intact. This is a design risk, not evidence that any real object was lost.

Until a durable, separately reviewed deletion/reconciliation and legal-hold protocol exists, `runKycRetentionTick` defaults to **no external purge** and permits that path only when its caller explicitly supplies `{ nodeEnv: 'test' }`. The worker passes its validated `NODE_ENV`. In non-test environments or with no option, it still runs the KYC expiry/restriction transaction, emits `kyc_retention_purge_disabled`, and returns without querying approved deletion requests, deleting objects or marking them purged. Existing approved requests remain pending; the warning requires monitoring. This is a deliberate behavior change: automated external KYC deletion is not available outside tests, so retention/legal obligations must be managed separately rather than assumed complete.

The application guard is not a security boundary against privileged code or DB/storage operators, and a deployment misconfigured as `NODE_ENV=test` can bypass it. Test mode must never use real data. This does not protect against other storage deletion paths, secure-delete backups/WAL/replicas, define how to restore already lost objects, reconcile existing inconsistent cases, or establish legal compliance. Re-enablement needs independently reviewed authorization, legal-hold timing, an explicit state machine with durable per-object evidence and idempotent operations, crash/commit ambiguity handling, retention/backup policy, observability and full failure-injection tests. Do not assume a new flag alone is sufficient.

Service unit tests cover omitted, development, staging, production and unexpected environment values, showing expiry can commit but no purge query or storage deletion occurs. The disposable PostgreSQL integration test checks an actual approved request and two synthetic encrypted objects remain intact in non-test modes. In test mode it injects failure after deleting the first synthetic file and demonstrates that DB rollback leaves the request/metadata unchanged while that file remains missing; it then exercises the existing retry behavior. These tests are not a substitute for live-storage behavior or a legal review. No hosted database, real object, worker configuration or deployment was changed.
