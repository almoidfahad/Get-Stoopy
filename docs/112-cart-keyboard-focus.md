# Cart line controls: keyboard focus during updates

A keyboard user activating a cart line update lost focus to the document body when the pending request disabled its button. The same happened after an explicit request failure. The cart line controls now stay focusable and expose `aria-disabled` while blocked, including during a request, an uncertain result and at quantity limits. Each handler explicitly checks its blocked state, and the existing in-flight guard prevents duplicate requests even before a render. A polite status reports an update in progress. Uncertain outcomes continue to block that line and direct the user to reload and review; no automatic retry was added. Removing a line may still remove the focused element after a successful refresh; focus placement after removal is not addressed here.

Local checks: 608 unit/component tests, typecheck and a production web build in a temporary copy passed. At 320, 390 and 1440 CSS pixels, Chromium with a synthetic cart API/session and intercepted delayed rejection verified focus through pending and failure, keyboard repeat suppression, selected Axe scans and no document overflow. Sixteen default, unconfigured routes were also scanned at 320 CSS pixels for Axe violations, horizontal overflow, a single h1 and HTTP status; the native mobile menu opened by keyboard and closed on navigation. Those scans exercise only those specific states; automated tools cannot establish full accessibility.

This does not cover a real identity provider, a real cart or checkout, all request outcomes, screen readers, real mobile devices, all zoom/browser combinations, or every privileged workflow. Sign-in, payment, address persistence and ordering remain incomplete/unconnected. No user database, Supabase project or production deployment was used or modified.
