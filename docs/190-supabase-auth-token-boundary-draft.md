# Supabase Auth access-token boundary: synthetic draft

## Existing behavior and why an adapter is necessary

The current storefront uses an OIDC/Keycloak BFF flow: a Keycloak ID token is verified by `apps/api/src/auth/id-token.ts`; `SessionService.createFromIdToken` finds/creates an identity, checks inactive users and email-linking conflicts, and creates an encrypted opaque local session. The BFF keeps a session cookie; `SessionService.resolve` loads server-authoritative roles, geographic scopes, vendor memberships and rider eligibility. Existing role checks are not just token claims. The shared Supabase project also has an existing `auth.users` trigger creating an editorial `public.profiles` record and its own editorial role policies. A Supabase access JWT is **not** interchangeable with the existing Keycloak ID token; reusing the current `/auth/session` endpoint without a deliberate identity/session migration would be unsafe.

## This increment

`apps/api/src/auth/supabase-access-token-draft.ts` is an **unwired** candidate verifier tested only against synthetic signed tokens and an in-process trusted JWK set. It is not imported by controllers, auth services or frontend, and it has **no environment gate**; do not wire it into production or rely on it as a login. It adds no dependency or Supabase connection and cannot access a key service on its own. No hosted Auth configuration, trigger, user, permissions or secrets are modified.

Given an explicitly trusted HTTPS `/auth/v1` issuer and a caller-supplied trusted key resolver, it verifies the JWT signature with RS256 or ES256, exact issuer, single `authenticated` audience, required finite integer `iat` and `exp`, UUID subject/session ID, Supabase `authenticated` role and explicit `is_anonymous: false`. It rejects expired/future-issued/not-yet-valid tokens, invalid claims, non-asymmetric algorithms and oversized token strings. Its only successful output is a draft marker, issuer, subject, provider session ID and expiry; email, `user_metadata`, `app_metadata`, and permissions are never returned or mapped to an admin/vendor/rider/customer role. Errors are generic and do not intentionally echo the token or key-lookup details.

These are **deliberately strict candidate assumptions, not a claim that every valid Supabase session has this exact shape**. The actual project's signing algorithm, issuer, JWKS rotation, aud, `session_id` and `is_anonymous` claim behavior have not been verified. Legacy HS256 projects or missing claims will fail closed; do not obtain or expose a shared JWT secret merely to bypass that restriction. The expected issuer and key resolver must come from fixed, trusted, reviewed server configuration—not token `iss`/`jku`, browser data or arbitrary request input. The tested `jose` resolver is local; network discovery, key caching/rotation and provider failures are not implemented or verified.

A valid JWT signature and expiry do **not** establish current Supabase session/user status, logout/revocation, email/phone verification, account lock state, MFA or recent step-up, local marketplace membership, role or authorization. The token verifier does not query any database or provider, bind a session cookie, refresh tokens, create a user, enforce CSRF, check replay, perform identity linking, protect credentials, or enable COD. Passing it is not a safe standalone authorization decision. Some of those guarantees may require live Auth checks or different session design; choose only after mapping performance, provider semantics, costs and threat model.

## Tests and remaining work

Synthetic unit tests use locally generated RSA/EC keys to exercise successful signatures, issuer/audience/role/anonymous constraints, invalid or missing IDs and times, nonfinite values, untrusted keys, unsupported symmetric signing, generic errors and ignoring malicious-looking metadata. They do not connect to the real project or establish claim compatibility. Existing Keycloak tests still pass; its production flow is unchanged.

A reviewed implementation must first confirm the intended Supabase project and how editorial identities are preserved, choose authoritative status/revocation checks and safe issuer/JWKS configuration, bind verified `(issuer, subject)` to marketplace users without automatic email-based takeover, preserve local authorization/version and privileged step-up, design Auth email/OTP/reset/signup and account linking, protect session/refresh tokens, and demonstrate logout, cross-user isolation, admin/vendor/rider/customer negative tests and actual Supabase integration in a safe test environment. Shared Auth triggers and redirects must not be altered without specific approval. Supabase Free plan does not automatically host the existing Nest API, Redis worker or production storage adapter. No migration or launch is authorized by this isolated draft.
