# Rider dashboard UI foundation

This first rider dashboard increment is a responsive **layout only** at `/rider`, inspired by `references/file_00000000a7508210a16ca15694141f4f.png`: dark sidebar, workspace header, overview cards, live-delivery, earnings, delivery-history and performance panels. The screenshot's sample names, numbers, locations, map, duty toggle, support claims and action buttons are not presented as real data. Unavailable modules are non-interactive text rather than links to missing pages. This is not the complete rider portal or an approved pixel match.

The page reads only the existing `/auth/me` session response and distinguishes signed-out, unavailable, no eligible rider profile and profile-present states. It does not render rider/user IDs or CSRF tokens. The layout and unavailable placeholders are visible without a session because they contain no rider-specific information. The profile indicator is informational, **not authorization**: any future rider data, shift controls, assignments, location, delivery proof and finance actions require independent backend authorization and appropriate rider/assignment scope. No duty state, offer, map, real delivery, location, wallet, payout or reporting is connected in this UI increment. Existing APIs are not represented as connected by this dashboard.

Server-rendered tests cover session states, malformed responses, unavailable reporting, missing feature links and absence of sensitive fields. They mock the session endpoint and do not prove live authentication, backend authorization, data isolation, browser interaction, mobile visuals or accessibility. The Vercel preview lacks backend configuration and should show the access-unavailable state. The remaining rider and vendor workflows, scoped admin dashboards, real data integration and visual review remain open.
