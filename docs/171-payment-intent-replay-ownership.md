# Sandbox payment intent replay ownership

`PaymentsService.createIntent` previously looked up `(orderId, commandKey)` using a privileged transaction and returned an existing intent before checking whether the caller owned the order. A signed-in user who knew another buyer's order ID and command key could retrieve the sandbox intent's returned fields. A command key is an idempotency token, not an authorization credential. The affected path is the sandbox adapter; live providers remain disabled. This review does not establish whether any request was actually made or data exposed.

The service now first locks the order with both its ID and the authenticated buyer ID, returning the same `ORDER_NOT_FOUND` for missing and non-owned orders. Only then does it check for an existing intent. The order lock also serializes concurrent creation/replay requests for that order. The replay lookup remains before the payable-status check so a buyer can replay a matching command even after payment status changes; conflicting payloads still fail. The change does not affect intent reads, sandbox webhook processing, cancellation or the separate non-test order-creation gate.

Service-level mock tests check authorization ordering and query parameters, matching replay after payment, and conflicting payload behavior. The disposable integration test additionally covers a different signed-in buyer using both a known key and an unknown key, simultaneous same-key owner requests, owner replay after verification, and a denied replay after verification. Simultaneous requests alone do not prove observed lock contention. The integration test must still run against real PostgreSQL/PostGIS/Redis; GitHub Actions has been blocked before job start by account billing. Mock tests do not establish database lock scheduling. This fix does not make payment, checkout, sandbox use with real data, or the wider privileged API production-ready. No hosted database migration or production deployment is included.
