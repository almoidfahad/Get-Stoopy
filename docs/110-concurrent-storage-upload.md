# Concurrent private-object upload safety

Two requests using the same valid upload token could both observe `PENDING_UPLOAD`, write different bytes to the same local object key, then update the database. This could produce two successes or inconsistent stored bytes and SHA-256 metadata. The upload transaction now locks the owner-scoped `StorageObject` row before checking its state and before writing the file. The first successful writer completes normally; a later waiter observes the changed state and receives `OBJECT_NOT_PENDING`. Existing token checks, owner predicate, RLS, size and magic checks, quarantine rules and audit remain in place. No schema migration is required.

The database row lock is not a distributed storage implementation or an atomic transaction with the filesystem. A filesystem write followed by transaction failure can leave a file while the database is still pending, and a retry may overwrite that file. The lock only coordinates writers sharing the same database and storage arrangement. Local encrypted filesystem storage is not suitable as a shared durable production object store across independent server instances. Upload token retries do not replay success, and long waits or storage operations can still hit transaction timeouts. These issues need a separate storage architecture and reconciliation design; this change does not authorize live KYC, payments, or file handling.

Local verification: 599 tests, typecheck and API build passed. Mocked service tests assert owner-scoped locking happens before file writing and that missing or non-pending objects are not written. A PostgreSQL-backed integration regression holds the fixture object row, overlaps two different uploads, checks one succeeds and the other is rejected, verifies downloaded bytes against the winning hash, and checks another user cannot use the token. It must run on isolated CI; no Supabase or user database was contacted or changed.
