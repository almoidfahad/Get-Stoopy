# Conservative cache policy for the versioned API

The earlier middleware in `docs/159-private-commerce-cache-policy.md` covered only `/api/v1/commerce`. Other versioned routes can also return private data: for example, `/auth/me` includes a CSRF token and account context, and order, payment, refund, delivery and administration routes can expose account-specific information. Cookie-authenticated responses should not rely on the browser, an intermediary or a caller to infer an appropriate cache policy.

The middleware now sets `Cache-Control: no-store` for **all** `/api/v1` responses, registered before CORS and body parsing, as well as authentication, guards, validation and controllers. This includes successes, errors, missing routes and preflight responses under that prefix. It conservatively includes public catalog, health and capability responses too; this may reduce cache effectiveness and increase backend load. Any future public cache exception requires a separate review of route sensitivity, errors, headers and intermediary behavior. Routes outside this versioned prefix, including `/api/docs`, are not covered by this change. Existing route-level no-store headers remain in place.

Local Express tests exercise the middleware's prefix, response, early parser error and preflight behavior. The repository's Nest integration tests additionally check authentication, order, capability and early-error routes; they passed in the PostgreSQL/PostGIS/Redis CI run `43163598927` attempt 2 on `df1822d`. The header instructs compliant caches not to store the response, but a later handler or infrastructure can override it, and malicious/non-compliant caches, service workers, browser extensions, proxy/CDN configuration and logging require independent review. This is not evidence of end-to-end privacy compliance. No hosted configuration, database migration or production deployment was performed.
