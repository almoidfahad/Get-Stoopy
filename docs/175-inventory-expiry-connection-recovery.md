# Inventory expiry connection recovery

Checkout quotes can reserve stock even though non-test order creation is disabled. Expiry is opt-in and must be running and monitored for abandoned reservations to be released. Previously `runInventoryExpiryTick` acquired a database connection outside its error handler. A transient connection rejection escaped the tick and could terminate the fire-and-forget inventory expiry loop rather than being retried, leaving stock reserved until intervention or restart.

The connection acquisition is now inside the tick's error boundary. A failed acquisition logs `inventory_expiry_failed` with a generic error code and zero expired, returns normally, and permits the existing polling loop to try again on its next iteration. If a query or commit fails after prior per-unit commits, their count is still returned; rollback is attempted only when a client was acquired, and the client is released. Error text is not logged because database messages can contain sensitive connection details or values. Unit tests cover a connection failure followed by a successful tick, partial committed work, rollback failure, release, and log redaction.

This only addresses rejected connection attempts and query failures in the inventory expiry tick. A stalled connection or query, process termination, disabled or unscheduled worker, prolonged outage, a failing logger, direct database writers and insufficient throughput still need independent operational handling and monitoring. Returning zero on failure is not proof there was no expiry backlog: alert on the failure event and separately measure backlog age. Other worker loops have not been changed by this increment. No worker was enabled, hosted database changed, or production deployment performed.
