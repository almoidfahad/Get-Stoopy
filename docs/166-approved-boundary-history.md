# Approved geographic boundary history prerequisite

The geographic design requires approved boundary versions to remain immutable before an active-pointer system can safely reference them. Migration `0075_approved_boundary_immutability` adds a `BEFORE UPDATE OR DELETE` trigger on `BoundaryVersion` for **all geography types**. An already-approved row cannot be updated (even a no-op, including removal/change of approval) or deleted. Unapproved proposals can still be edited. An update that first sets `approvedBy` must not simultaneously change the proposal's ID, owner, version, geometry bytes, source, effective time, hash or creation time. New approved versions are inserted separately rather than rewriting historical versions. Existing rows are not backfilled, rewritten or automatically activated.

The disposable PostgreSQL/PostGIS suite checks permitted draft editing, rejection of modified-at-approval data, approved-field and geometry edits, deletion including by the table owner, and a concurrent edit waiting behind approval. A rollback-only upgrade rehearsal installs the migration with an existing approved row and verifies its bytes/metadata are unchanged and the guard applies. The same-zone preview race fixture now uses an isolated zone and preserves both approved versions instead of deleting one for cleanup.

This is a **prerequisite**, not an activation system or complete authorization control. Existing privileged insert grants still permit direct insertion of an already-approved row; the trigger does not verify approver identity, maker/checker separation, geometry/hash correctness, geographic scope, audit, overlap or a valid active pointer. An owner/superuser can alter or disable triggers. The active-boundary pointer, proposal/review authorization, active overlap policy, transaction ordering, immutable reference snapshots and deployment upgrade plan still require design and testing. Existing invalid or conflicting history remains untouched and can still make previews fail closed. Do not delete approved history as a workaround.

Migration 0075 is committed for disposable CI only and has **not** been applied to the user's hosted database. Before any rollout, inventory existing boundary rows, writers and dependencies; assess blocked historical update/delete workflows and migration ownership/locks; back up and rehearse in an isolated database. The shared Supabase project contains other application data and is not an isolated test target. No live configuration, checkout or deployment changed.
