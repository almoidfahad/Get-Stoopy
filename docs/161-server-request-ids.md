# Server-generated API request IDs

The API no longer trusts incoming `x-request-id`. Even an apparently safe alphanumeric value may contain a phone number, name, token or other identifying text and would previously have been copied into application and error logs. Each request reaching the API application now gets a fresh server-generated UUIDv4, returned in the `x-request-id` response header and included in normal request logs and Nest error response bodies. Client-provided values are not propagated or logged by this middleware; repeated requests with the same incoming value receive different server IDs.

Request context registration moved from Nest route middleware to early Express middleware in `createApp`, before CORS and Nest's parser. This provides correlation for ordinary early parser failures and CORS preflights as well as matched and unmatched routes. As there is no resolved route for these early responses, the request log uses `[unmatched]`. The middleware is registered once. Request logs record completed responses; connection aborts, failures outside the Node application and failures before this middleware are not covered.

This is a deliberate correlation compatibility change: systems that previously searched API logs using an inbound request ID must instead capture the server's response ID, or design a separately reviewed trusted tracing mechanism. Browser cross-origin code cannot necessarily read this header without an appropriate CORS expose-headers policy; existing error bodies also carry the ID. Database audit IDs are separately generated and are not automatically linked. Tests check uniqueness, malicious-looking incoming IDs, normal and error response/log correlation, preflight and malformed JSON in the Nest integration app, and that the app request log omits a synthetic body marker.

This does not sanitize exception messages, nonproduction stack traces, request/response bodies, upstream gateway access logs or third-party tracing. Production infrastructure, logging, retention, CORS and privacy controls still need review before real recipient data. No hosted database or deployment changes were made; the recipient draft remains test-only.
