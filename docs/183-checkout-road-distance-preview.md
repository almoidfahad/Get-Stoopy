# Synthetic multi-store road-distance preview

This increment adds `POST /api/v1/commerce/carts/{cartId}/recipient-draft/road-distance-preview` for **disposable test environments only**, using a saved encrypted test recipient draft. It calculates one independent road distance from each cart store's approved pickup point to the recipient destination. These are separate point-to-point distances, **not** an optimized multi-stop route, rider-to-store distance, map, route polyline, final trip, fee or order. The response explicitly says `TEST_ONLY`, `quoteBound: false`, `coverageGuaranteed: false`, `orderAvailable: false`, and null fee/total. Distances over the requested 3 km limit are reported as measured rather than silently truncated or treated as eligible. The endpoint does not enable COD or store/reserve any order.

The service rejects non-test environments and missing test encryption keys before a DB transaction. Even in test, the route endpoint must be explicitly enabled and point to an HTTP `127.0.0.1` stub with an explicit port and no credentials/path/query/fragment; HTTP redirects are rejected. This prevents a direct request or redirect to a live map provider, but the local stub itself must be trusted not to forward data. Test mode and local stubs must never receive real customer data. The stub request includes synthetic coordinates but not recipient name, telephone or address. The API response and error messages omit coordinates and contact details, uses `Cache-Control: no-store`, requires a session and CSRF, and rechecks cart ownership and the draft version.

Before routing, a repeatable-read transaction revalidates the buyer's saved draft, cart, approved unambiguous zone and all stores' coverage and approved pickup points. It rejects more than 25 distinct stores, missing pickup points, stale or expired drafts, and invalid provider matrices; it never guesses a route or falls back to straight-line distance. The provider call is outside the database transaction, and a fresh snapshot checks the same cart/draft versions, expiry, coverage and pickup IDs, versions and coordinates afterwards. Changes or expiry cause refusal; a provider failure returns a generic error. A later change can occur after the final check, so results remain a snapshot, not an authorization, guaranteed current route or quote. No provider latency, cost, connectivity or real-world routing claim is established.

Unit tests verify production/staging/development rejection and block nonlocal/malformed stub URLs without opening a DB transaction. Disposable PostGIS integration uses a local synthetic HTTP stub with two real fixture stores, validates ownership/CSRF/no-store and privacy, independent meter values and malformed response denial, and pauses the stub while a cart changes to ensure stale results are rejected. No real maps, addresses or provider requests are used.

A production map requires a separately reviewed mapping/routing provider, API key handling, cost and customer location privacy decisions, coverage boundaries, address/geocoding accuracy, rate limiting, network-failure/retry policy, map geometry/attribution, and accessibility. Checkout still needs authoritative route/fee snapshots, the owner's multi-delivery customer charge rule, Purbadhala's ৳30 total cap, COD collection allocation, secure identity, and isolated production infrastructure. The test-only gates and multi-store COD guard remain in place. No hosted DB, config, external provider or deployment was changed.
