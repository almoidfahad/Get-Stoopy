# Prisma types and local diagnostic setup

A fresh dependency install may leave `node_modules/.prisma/client` as the default `@prisma/client` placeholder because this repository's schema is in `packages/db/prisma/schema.prisma`. TypeScript then reports many downstream missing/inferred-any types. CI avoids this by running `npm run db:generate` before typecheck. `npm run setup:dev` now provides the documented local sequence: generate the actual project client and build workspace packages. `pretypecheck` checks for project-specific type markers and gives an actionable error when they are missing; it does not disable strictness or suppress compiler errors. It is a prerequisite check, not proof the client is current or a runtime engine works.

In this sandbox the normal Prisma engine download failed because the configured network could not establish TLS to Prisma's engine host. For diagnosis only, project types were generated locally using Prisma's `--no-engine` mode and the typecheck passed afterward. That client does not provide a usable normal database engine and is **not** a validated backend or a recommended application setup. The standard `setup:dev` must succeed with trusted engine downloads on the developer's machine. CI uses the standard generation and both its validate and isolated-DB integration jobs passed on the prior commit. No TLS verification was disabled and no Supabase or production database was touched.

The user's reported number of errors could originate elsewhere; without the actual error list the exact set is not confirmed. Request the first error messages/file paths (with secrets removed) if diagnostics persist. No claim is made that an HTTP 414 issue, editor-specific problems, or a runtime database integration was reproduced or fixed.
