# Session and linking ID-token claim validation

The API verifies an ID token's signature, issuer and audience before using it to create a session or link an identity. Previously, `exp` and `iat` were not required by the JWT verifier, and `String(payload.sub)` could turn a missing or non-string subject into a truthy identity key such as `undefined`. Both paths now also require `sub`, `iat` and `exp`; the subject must be a nonblank string of at most 255 characters and timestamps must be finite numbers. The opaque subject is preserved exactly, not trimmed or coerced. JWT verification still checks expiration, issuer, audience and the signing key, and errors remain a generic 401 before any database transaction.

This narrows accepted inputs; a provider omitting these OIDC-required claims must be corrected before sign-in can work. It is not a complete OIDC security review: real provider connectivity, token lifetime/clock policies, multiple-audience/authorized-party handling, replay protections, nonce flow and end-to-end sign-in need separate verification. This does not deploy an identity provider or change existing sessions, and does not add any database migration.

Verification: 24 tests use real RSA-signed JWTs and a local in-memory JWKS, with mocked transactions, including missing and malformed claims, non-finite numeric timestamps, expiration, issuer/audience and signature failures, and a valid opaque subject. Invalid tokens are checked not to start a database transaction. Session and identity-link paths are covered, including the administrator step-up guard. The complete local suite passed 575 tests; typecheck and API build passed. No external identity provider or user database was contacted.
