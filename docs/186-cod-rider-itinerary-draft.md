# Rider route distance: first store through delivery

For the 3 km per-rider maximum and distance slabs, the owner selected **first pickup store → any subsequent pickup stores → customer**, excluding the rider's approach to the first store. This specifies the distance basis, not how stores are assigned to riders, how their visit order is selected, how distance is fixed before checkout, or how to handle a route change after the customer sees the price.

`packages/core/src/cod-rider-itinerary-draft.ts` is an unexported, unwired arithmetic check for a caller-supplied ordered sequence of distinct synthetic store IDs, one destination ID, and the exact consecutive leg distances in integer meters. It rejects missing, reordered, disconnected, negative, non-integer and unsafe leg values, and rejects the entire itinerary if its total exceeds 3,000 m. It returns the tier based on the **sum**, not the individual leg tiers. A maximum of 50 stores is a defensive software limit, not an operational capacity policy. IDs must be stable, non-personal tokens; their format cannot verify identity or privacy.

This calculation does not obtain routes, verify origin/destination coordinates, select travel mode or stop order, check whether distance data belongs to the given points, group stores into rider assignments, handle traffic or route recalculation, or determine a customer charge. Independent store-to-customer distances in the existing synthetic matrix preview cannot be summed as an itinerary. A production route provider and map can disclose coordinates and incur charges; using one needs separate privacy, cost, map and reliability review. Tests verify synthetic itinerary sequencing and distance boundaries only.

The selected highest-slab-once rule (`docs/185`) still needs trusted complete rider itineraries, authoritative checkout totals, per-delivery cash allocation and database/ledger changes. Production order creation remains disabled; no hosted database, external provider, live backend, or site deployment was changed.
