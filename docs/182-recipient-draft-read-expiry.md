# Test-only recipient draft read: expiry recheck

A buyer-owned encrypted recipient draft is logically hidden at its expiry time. Its GET path previously checked the database wall clock only before decrypting, so if decryption/validation took the request across the expiry instant it could still return contact and location data from that expired draft. The saved-preview path already performed a second check. GET now rechecks the database wall clock after successful decryption and returns the same metadata-only `EXPIRED` result, with `draft: null`, if expiry is reached. Equality with expiry is expired. It still does not decrypt an already-expired row. Cache-Control remains `no-store`.

This is a narrow privacy improvement to the existing **test-only** draft, not production checkout or a new recipient feature. It is not atomic with delivery of the HTTP response: time can pass after the final check, and repeatable-read snapshots can still return an older draft when a concurrent clear/save commits after the snapshot was taken. Clients should not treat a draft read as an authoritative quote, active serviceability or a guarantee against concurrent edits. Logical expiry is not deletion or secure erasure of rows, WAL, replicas, backups or logs. Worker operation, key lifecycle and privacy review remain unfinished; see `docs/153`, `docs/154` and `docs/155`.

Unit tests cover exact expiry before and during read, an unexpired encrypted draft, non-owner cart rejection and the production gate. Disposable PostGIS integration stubs only the wall clock around a real encrypted draft read to exercise the expiry crossing, checks no contact/location is returned and preserves no-store; the actual snapshot, ownership and storage behavior are otherwise unchanged. No hosted database, worker, production configuration, order gate or deployment was changed. COD still requires resolved distance tiers, an authoritative total and isolated verified infrastructure.
