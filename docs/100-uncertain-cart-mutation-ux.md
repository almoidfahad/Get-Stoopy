# Uncertain cart mutation UX

When an add-to-cart request fails at the network level or returns a server error, the outcome can be unknown: a request may have reached the service and could still complete. The UI now flags that uncertainty, links to the cart, and disables adding again until the shopper explicitly acknowledges the warning. Editing the option or quantity does not dismiss the warning. Explicit 4xx rejections remain normal errors. For an uncertain cart-line update or removal, that line's controls are disabled and a cart reload is offered, with the same warning that the earlier request could still complete later. There is no automatic retry.

This is a **client-side guard, not idempotency or a guarantee against duplicate changes**. The uncertainty is held only in the mounted component and is lost on reload/navigation; other tabs or other cart lines are not locked. A reload or a manual acknowledgement cannot establish that an earlier request will not complete later. Durable server-side mutation idempotency and reconciliation would need separate design and testing.

Unit/component tests exercise network and server errors, 4xx rejection, edits while uncertain, explicit acknowledgement and line-control recovery. A locally built web server with a synthetic catalog/session and browser-intercepted cart requests was checked at 320, 390 and 1440 pixels for keyboard operation, blocking and acknowledgement, selected Axe checks and overflow. No real cart mutation, sign-in, backend or production deployment was used. Typecheck, build and 530 tests passed locally; this does not replace a real-device, screen-reader or end-to-end audit.
