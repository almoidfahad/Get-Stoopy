# Draft order-level delivery-charge cap check

The owner requires that the **total customer delivery charge** for an order to Purbadhala Sadar, including an order involving multiple stores or riders, never exceed ৳30 (3,000 BDT paisa). Checking each store's fee against ৳30 independently is insufficient: two fees of ৳20 each would exceed the order cap.

`packages/core/src/cod-order-pricing-draft.ts` adds an isolated arithmetic validation of explicitly supplied, already-allocated **store-group pricing components**. It uses the existing pricing calculator to sum all supplied customer delivery fee components, requires a caller-supplied supported area and BDT, and rejects a Purbadhala total above 3,000 paisa. The cap is on customer delivery charges, not product value, tax, the total payable, or rider compensation. Product-only discounts cannot offset an excessive delivery-fee component. No comparable order-level Mymensingh cap has been specified, so none is inferred. This checks supplied values only: zero is accepted as arithmetic input, not approved as a free-delivery policy. It does not select or allocate a fee, determine a customer destination or serviceability, assess individual rider distances, or prove the supplied figures include every fee. Passing does not establish that a price is fair, approved, or accurate.

This module is not exported by the core package barrel, invoked by an API, or bound to a cart, quote, order, delivery, or ledger. Its result is marked `DRAFT_VALIDATION_ONLY`, not an authoritative quote or permission to order or collect cash. The owner has not decided how the multi-delivery fee is chosen or allocated. Store-group allocations are merely an existing arithmetic input shape and do not represent actual rider assignments. Discounts are product-only in this calculator; delivery promotions, other charges, currency conversion and partial delivery/cancellation/refund rules need separate policy. No hosted data, migration, deployed configuration or live COD availability changes.

Synthetic unit tests check 2,999/3,000/3,001 paisa boundaries, the sum of multiple individually permissible fees, the distinction between delivery and product/tax amounts, currency and input failures, arithmetic overflow, and 50 explicit allocations. For future use, a production design must independently bind every customer-facing delivery charge and authorized reduction to an immutable order snapshot and currency, define treatment of cancellations and additional fees, verify actual service area, and enforce the cap across every supported order/update path (including concurrent writes and database constraints). This unwired helper does none of that; do not weaken the production order gate or multi-delivery COD guards on the basis of these tests.
