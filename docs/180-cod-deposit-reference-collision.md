# Conservative COD deposit-reference collision guard

The existing deposit uniqueness constraint is `(riderId, method, externalReference)`. It does not prevent the same submitted reference from being independently verified for two riders or under two methods, potentially posting multiple journals and reducing custody twice for what a reviewer may believe is one company receipt. This is a design risk, not evidence of an actual duplicate or real financial loss.

The review service now acquires a transaction-scoped advisory lock derived from the country and stored reference before checking for any **other verified** deposit with that same country and exact stored reference. If found, verification fails with `409 COD_DEPOSIT_REFERENCE_ALREADY_VERIFIED` before allocation, journal, audit or state change. The guard is deliberately conservative across riders, methods and currencies. Pending/rejected deposits do not block verification, rejecting a pending item is still possible, and an already-verified same-command replay still returns normally. The country/reference lock always precedes the existing rider/currency allocation lock. The database's text equality is used as-is: submitted references are trimmed on input, but no case folding, Unicode normalization, punctuation cleanup, bank/account identity or cross-country matching is assumed.

A matching reference can legitimately occur across separate banks, merchant accounts, office receipt systems, currencies or methods; these collisions need independent manual reconciliation. There is no automatic override in this change, and rejected deposits cannot simply be re-reviewed. Conversely, different spellings/references can represent the same actual deposit. A rider-supplied string and even an evidence hash are not trusted proof; reviewers must still independently match a real company receipt/statement and verify its identity, ownership, amount, currency and status. This is **not** an authoritative provider reconciliation or a uniqueness guarantee for actual money. No external bank or MFS lookup occurs.

The protection covers concurrent reviews through this service, not direct privileged DB writers, older duplicates, other programs, different references, other countries or a deployment running older code. The PostgreSQL hash is only for coordination, not authorization or permanent identity; hash collisions can serialize unrelated references. Transaction commit failures can have an unknown outcome: retry/reconcile the same command before taking further action. Existing duplicate verified deposits are not altered, and the new guard does not itself identify, reverse or repair historic rows. Current collection amounts remain subtotal-only and multi-store COD remains blocked under `docs/179`.

Unit tests cover authorization, collision handling before ledger writes, review replay and rejection. Disposable PostGIS integration uses two completed synthetic single-store COD deliveries for different riders, submits the same reference under BANK and MERCHANT_MFS, deliberately holds the reference lock until both reviews wait, then verifies exactly one review, journal and allocation succeed; the loser remains pending and can be rejected. The test uses no real bank, cash or customer data. No hosted DB changes, migrations, workers, online payments or deployment are included.

A production design still needs trusted provider/statement or office receipt identifiers and issuer/account scope, canonicalization agreed with the source, idempotent one-to-one evidence matching, corrections/reversals and discrepancy queues, protected audit trails, DB-enforced cross-writer invariants, historical reconciliation, and operator procedures. COD checkout and money movement are not enabled by this guard.
