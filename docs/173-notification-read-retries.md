# Safe notification read retries

`markRead` previously updated the row and inserted an outbox event with a unique key on every call. A retry after success could fail on the duplicate event key, and simultaneous requests could race. The database transaction prevents a failed duplicate insertion from partially committing, but callers still receive an error instead of a reliable replay.

The service now locks the notification row by ID and owner before checking its status. An already-`READ` notification returns `duplicate: true` without changing `readAt`, adding another audit or inserting another event. For an unread notification the existing update/audit/outbox transaction still runs once and returns `duplicate: false`. The lock serializes concurrent service calls for the same row. Ownership and `notification.update` authorization remain required. This does not repair pre-existing inconsistent rows, control direct privileged DB writes, change which statuses may be marked read, or implement email/SMS/push delivery.

Service mock tests cover owner-filtered locking, no-op retry, single update/audit/outbox and missing rows. An isolated native PostgreSQL 16.13 synthetic-schema rehearsal ran the compiled service through a small `pg` transaction adapter: it observed a real second-connection lock wait and confirmed one update, one audit, one event and identical `readAt` across concurrent calls. It was not the actual Prisma adapter, real schema, PostGIS, Redis or the complete integration suite; the temporary private-socket server was stopped. The repository integration test includes simultaneous and subsequent retries and counts audit/outbox records; it passed in PostgreSQL/PostGIS/Redis CI run `43163598927` attempt 2 on `df1822d`. Simultaneous calls in that integration test do not by themselves prove they overlapped. No hosted database or production deployment was changed.
