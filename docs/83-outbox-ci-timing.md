# Outbox lease CI timing investigation

On commit `3f870c7`, GitHub push run `42468835833` failed `outbox-lease.test.ts` at the first failed-enqueue counter (`failed` was 0 rather than 1); the PR run for the same commit passed. The job annotation identifies the assertion but not whether the row was unclaimed or fenced. The run's full log download was inaccessible from this sandbox. The exact cause is therefore **not proven**; a single later pass does not prove a flaky test is fixed.

One concrete race in the test fixture is that `OutboxEvent.availableAt` is PostgreSQL `TIMESTAMP(3)`: a database `now()` default or update can round up by a fraction of a millisecond, so an immediately following claim can observe the row as not yet due. The integration fixture now explicitly makes inserted, retried and drained rows due one second before database time. The failed-enqueue test verifies the fixture is the sole claimable row and reports all batch counters plus the sanitized fixture state if it still fails. The backoff assertion now compares its deadline to a database timestamp recorded before publishing, rather than a potentially delayed runner clock. The lease fencing, failed-attempt count, backoff, error redaction and dead-letter assertions remain in place; no production outbox logic was weakened or changed.

These are test-fixture changes for the isolated CI PostgreSQL/Redis database, not any Supabase or production migration. CI must execute the full integration suite to validate them; repeated successful runs improve confidence but do not establish the historical root cause.
