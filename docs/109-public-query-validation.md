# Public catalog and destination query validation

The public product-list and serviceable-city endpoints now validate the actual runtime types of optional search parameters before using them. Repeated or nested values are rejected with a controlled `400` instead of being coerced into misleading strings or reaching application logic as arrays/objects. This matters with Nest's global transform pipe as well as Express query parsers. NUL characters are rejected before PostgreSQL text comparisons; existing search length limits and empty-search behavior are preserved. Optional city, category and cursor UUIDs are validated and normalized to lowercase; country IDs are also normalized after the existing UUID pipe. This avoids valid uppercase UUIDs failing case-sensitive comparisons with PostgreSQL's lowercase ID output.

The change is limited to these two public endpoints. Other API queries have not been audited by this slice. It changes invalid-query behavior; consumers must send each parameter at most once. It does not enable catalog, sign-in, checkout, or a database connection.

Verification: 21 local HTTP tests use real Nest controllers, production-equivalent validation pipe and exception filter with mocked services, including repeated/nested inputs, NUL, search boundaries, valid filters and uppercase IDs. The test configures Express's extended query parser to exercise nested inputs in addition to repeated parameters. The complete local suite passed 596 tests; typecheck and API build passed. PostgreSQL-backed regression cases have been added to isolated CI; no Supabase or user database was contacted or modified.
