# No-store on private commerce responses

Buyer-specific commerce responses now receive `Cache-Control: no-store` from a path-scoped Express middleware mounted at `/api/v1/commerce`. The middleware is registered before CORS, Nest's body parser, guards, pipes and controllers, so successful responses and errors—including unauthenticated/CSRF rejection, malformed JSON, validation, missing carts, conflicts and internal failures—are covered. It also applies to all current and future routes under that commerce prefix, not just recipient drafts. Existing route-level headers remain as defense in depth. Other API prefixes are not changed.

Disposable API integration tests cover successful cart and draft reads, 401, 403, 400, 404, 409, 503 and preflight responses, including malformed JSON and corrupted test ciphertext. This header instructs compliant browsers and intermediaries not to store responses; it does not prevent malicious caches, request-body or database logging, reverse proxies that ignore/override the policy, or exposure in URL paths. Separately configure and verify CDN/proxy, TLS, request/response logging, privacy review and retention. The draft still is hard-disabled outside tests and is not connected to checkout; this change does not make the feature production-ready. No hosted database, configuration or deployment changed.
