# Sign-in readiness and callback recovery

The login page checks the same required web configuration as the sign-in start route at request time. If required settings are missing, it gives a generic unavailable message and omits the sign-in link instead of sending the buyer to a known failure. It does not reveal which setting is missing. If settings are present, the link is offered; this is not a connectivity, provider health or successful-login check. Browsing remains available in either state.

The sign-in callback now handles missing configuration and transaction-cookie read failures as well as provider and backend errors. It clears the transient transaction cookie and returns a non-cacheable, relative recovery redirect with no callback query or error details; it sets no session on those error paths. Both failure and success responses use a no-referrer policy. The Next.js header configuration also overrides the site-wide policy for both sign-in and account-link OAuth callback paths; the latter has no other behavior change. The configured callback origin, provider exchange and backend session creation remain the authentication authorities. These changes do not add identity configuration, create a user, bypass authentication or enable registration/payment.

Server-render and route tests use mocked configuration, provider, cookies and API. A local built-server HTTP check covered the unconfigured login state, callback redirect, no-store/no-referrer headers and clearing the actual transaction cookie; it did not use a live identity service. Real identity-provider redirects, cookie behavior in browsers, live session creation, screen readers and production backend configuration remain unverified. This is an unmerged code change; it does not deploy to the public site or alter Vercel, Supabase or other live infrastructure.
