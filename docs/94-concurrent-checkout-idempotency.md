# Concurrent checkout quote idempotency

Quote creation takes a transaction-scoped PostgreSQL advisory lock for the buyer before checking the command key. Previously, two requests could both miss the existing quote, then the second would wait for the cart lock and return a reservation or cart-version conflict instead of replaying the first request. The buyer-scoped lock also serializes creation attempts across that buyer's carts before the existing active-quote count check. Different buyers remain independent except for hash collisions and shared stock/cart locking. The lock is not an authorization mechanism; existing ownership, RLS, stock, version and unique constraints still apply. It is released automatically at transaction end, including rollback; the existing transaction timeout still applies.

The integration regression tests deliberately hold a fixture cart row until two requests are blocked, then verify a single quote and stock reservation: an identical command returns the same quote as a duplicate, while the same key with changed input returns the idempotency conflict. Cleanup releases the quote and checks inventory returns to the prior value. These tests run against isolated CI infrastructure, not the user's Supabase project. They cover concurrent requests on one cart, not all cross-cart, expiry, release, multi-tab or network-failure races. No migration or production data change is included.
