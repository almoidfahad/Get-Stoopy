# Fail closed on ambiguous preview boundaries

The geographic design calls for an atomically managed active boundary pointer, but the implemented `ServiceZone` schema does not yet have one. The previous delivery preview accepted any approved effective version supplied by a caller, including a superseded polygon. Choosing the highest version or latest effective date would invent an activation policy. As an interim safety boundary, delivery preview now rejects a zone when more than one approved, effective boundary version exists for that zone. It does so regardless of which polygon covers the point. A future or unapproved version does not by itself block a preview. The same rule applies to saved-draft preview and draft save because they use delivery preview validation.

The database samples its clock once for the boundary query, and the existing repeatable-read transaction gives a consistent view of boundary rows and cart/service-area state. A boundary change can still commit during or immediately after a preview, so the response remains a nonbinding snapshot; expiry/activation timing is not a promise about the future. The generic `CHECKOUT_DESTINATION_NOT_SERVICEABLE` response avoids exposing internal configuration. A sole approved effective version is not proof that an administrator actually activated it: the active-pointer design, review/activation workflow, immutable history, audit and concurrency guarantees remain to be implemented before relying on it for checkout. Historical effective versions will cause conservative rejection once multiple versions exist; do not delete or alter approved history to work around this safeguard.

Disposable PostGIS integration tests check ambiguity even where only one of the two polygons covers the point, future/unapproved versions, both unsaved and encrypted saved preview, privacy/no writes and an interleaving where a competing boundary is inserted after the saved draft was read. The in-flight preview sees its earlier snapshot; the next request fails closed. No migration, hosted configuration, live deployment, order, or checkout activation is included. Existing dispatch and destination DB guards still use their older effective-approved rule and are **not** fixed by this change. They require the active-pointer design and independently tested enforcement before production use.
