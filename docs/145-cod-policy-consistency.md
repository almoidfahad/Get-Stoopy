# Cash on delivery: policy consistency and checkout boundary

The project instructions request cash on delivery (COD) and verified reconciliation. Existing backend foundations already include a country-scoped admin COD policy, policy-gated product-subtotal-only COD orders, delivery cash custody, and independently verified deposit allocation (see `docs/40-rider-earnings-cod-ledger.md`). They are not a complete customer COD checkout: recipient/address capture, delivery charges, tax and a confirmed total are not implemented in the storefront flow.

This increment hardens the existing backend policy boundary. Policy creation is serialized per country even if no policy row exists; existing policy updates lock the row before checking its version. COD order creation locks that same row until the order and its immutable policy snapshot commit, so a concurrent disable or limit change cannot be mixed with a stale policy snapshot. Administrative permission, geographic scope, recent step-up, owner checks and database guards remain. COD maximum input must fit a positive PostgreSQL signed bigint, returning `COD_MAX_INVALID` for oversized values.

The storefront now explicitly says cash on delivery is unavailable in checkout and explains that recipient details and the confirmed total including delivery charges are needed. It does not present a working order/payment action or claim cash is collected.

Disposable PostgreSQL tests cover concurrent first policy creation, conflicting same-version policy changes, both orders of an order-versus-policy-disable race, bounds rejection and stock/quote effects. Component tests check the unavailable COD notice. These test a product-subtotal-only backend foundation, not a real COD purchase, delivery, full reconciliation workflow or hosted operation. No policy was enabled in the user's database and no production deployment was performed.

Enabling customer COD safely still requires recipient/address persistence and validation, authoritative delivery/tax and total calculation, full order and delivery UX, transparent COD collection/reconciliation, end-to-end security and failure recovery, an approved operational policy and isolated hosted verification. Never treat an unverified rider deposit as paid. Existing direct privileged database writers must also follow locking rules; this change does not establish a universal database-level concurrency guarantee.
