# Dispatch and retention worker connection recovery

Like the inventory expiry worker (`docs/175`), dispatch expiry, test-only checkout draft retention and KYC retention acquired a pool client outside their tick error handlers. A rejected acquisition could escape the tick and terminate its fire-and-forget polling loop. Each now acquires the client inside the existing error boundary; on failure it logs an event and returns normally so the loop can attempt its next scheduled tick. Rollback and release are attempted only when a client was acquired. Invalid checkout draft batch sizes still fail explicitly before acquisition.

Dispatch and KYC errors now log stable generic codes rather than raw database/storage exception text; KYC purge failures also omit the request ID because those errors can contain sensitive paths and case data. This reduces diagnostic detail: operations must alert on the events and investigate through separately controlled channels. KYC's expired count is now assigned only after the first transaction's COMMIT reports success; previously a failed COMMIT could be reported as completed. Counts from earlier successful commits remain available if a later query fails. A network error during COMMIT can leave its actual outcome unknown, so zero is not proof that nothing committed; reconcile against durable state.

Unit tests cover failed acquisition followed by another successful tick for each worker, query/rollback failure and redaction, KYC confirmed versus unconfirmed expiry counts and sensitive purge-error logging. Existing disposable PostGIS integration exercises real dispatch expiry and KYC/draft retention; the new acquisition-failure cases use mocked pools. No changes were made to schedule, enablement, policies, DB schema or hosted services. Checkout draft retention remains test-only.

This does not resolve a connection or query that never returns, worker crashes, disabled/unscheduled workers, failed loggers, monitoring, throughput, or other loops. KYC object deletion happens outside PostgreSQL and cannot be rolled back with its transaction: a failure can leave storage and DB temporarily inconsistent, and deletion/backup/legal-hold operations still require independent review and reconciliation. Retention is not secure erasure of backups, replicas or logs. None of this enables production checkout, dispatch, KYC automation or live data processing.
