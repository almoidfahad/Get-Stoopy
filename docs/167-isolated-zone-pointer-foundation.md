# Isolated zone-boundary pointer foundation

Migration `0076_isolated_zone_boundary_pointer` adds an initially empty, owner-only `ZoneBoundaryPointer` table as a **structural test foundation**. Nothing in the API, preview, order, delivery or dispatch reads it, and no existing boundary is auto-selected or activated. It is not a production activation feature.

A row references one existing service zone and one boundary. A trigger requires the boundary to be an approved, effective `ZONE` boundary owned by that exact zone, with nonempty valid geometry within longitude/latitude bounds. It locks the boundary row while checking it. Initial version is 1; updates keep the zone fixed, change the boundary and increment the version exactly once; delete is rejected. Migration 0075 separately prevents ordinary edits/deletion of approved boundary rows. Pointer selection does not itself validate coverage overlaps, city status, authority, an authenticated audit record or policy. Migration 0077 adds experimental structural change history (docs/168), not an authenticated audit. There is no deactivation or audited rollback workflow yet.

FORCE RLS and a migration-owner-only policy are enabled, and both application roles and PUBLIC lose all table privileges. `scripts/db-grants.sql` explicitly repeats that revocation after its general inventory grants. Even with this guard, the migration owner or database superuser can change privileges, policies, triggers or data; do not treat owner access as a production approval workflow. Any new activation design must provide scoped authorization and independent review, audit history, explicit effective-time/overlap policy, safe lock ordering, deactivation, snapshot and quote/order/dispatch transaction semantics before application roles gain access or it becomes a source of truth.

Disposable PostGIS integration tests check empty initial state, mismatched/unapproved/future and invalid geometry rejection, versions, no deletion, concurrent stale updates, and application-role denial after grants rerun. No boundary or pointer is written to the user's hosted database. The migration has not been deployed; the shared Supabase project and its existing data are not an isolated test environment. The existing conservative preview checks remain in force, and checkout/order activation is not changed.
