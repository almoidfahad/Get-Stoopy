# Sign-in session response safety

After the OIDC callback, the web BFF previously cast any successful session API response to the expected shape. An unreadable or malformed 2xx could result in a bad session cookie and a misleading redirect to the account page, even though the API might have created a server session.

The callback now accepts the API's documented 201 only, with a 43-character base64url session token and a valid, future UTC expiry matching the API's serialized format. Redirects are not followed, and the session request has an eight-second timeout. Once the request starts, a failure, timeout, unexpected status, malformed body or cookie-write error is reported as an unconfirmed sign-in. The transient OIDC transaction is cleared and the response does not set a new session cookie; an existing session cookie is not silently removed. The sign-in page explains that an earlier browser session may remain signed in and that the server may have created another session. It offers an explicit retry, not an automatic one.

Verification: 791 unit/component tests, typecheck and an isolated production web build passed. Tests cover token/expiry shapes, expired and impossible dates, unexpected statuses, redirects, network/timeout, missing ID token, cookie-write failures and valid responses. At 320, 390 and 1440 CSS pixels, Chromium used a synthetic local OIDC provider and session API through the actual web callback: a server session was created but the response contained a malformed token; the interface warned, discarded the transaction and set no new session cookie, then keyboard retry with a valid response reached the fixture account. Selected Axe and overflow checks passed. Additional checks covered an existing browser cookie, a stalled request that completed later, and a JavaScript-disabled callback. The fixture is not a real identity provider or production authentication system.

The token and expiry checks validate response shape only; they do not authenticate the session or verify backend ownership. An unconfirmed request may leave a server-side session until it expires or is revoked; retrying is not durable idempotency, and an existing session remains unchanged. Real Keycloak, full accessibility/device, cross-tab and real-backend testing remain outstanding. No Supabase connection, user database change or production deployment was performed.
