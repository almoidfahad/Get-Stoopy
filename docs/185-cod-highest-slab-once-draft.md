# Highest-slab-once customer delivery charge: draft

After initially deferring the multi-delivery customer charge, the owner chose **the highest applicable rider-delivery slab once per order**. For example, a Mymensingh order with ৳20 and ৳40 slabs has one ৳40 customer delivery charge; a Purbadhala order with ৳20 and ৳25 slabs has one ৳25 delivery charge. Purbadhala's total customer delivery charge must never exceed ৳30. The existing area-specific tier amounts and 0–1 / >1–2 / >2–3 km bands remain as in `docs/181`. Every rider delivery is subject to the 3 km maximum; an invalid or over-limit delivery must not be ignored merely because another delivery has a valid slab.

`packages/core/src/cod-delivery-order-fee-draft.ts` applies that selection to a nonempty, explicit synthetic list of rider-delivery distances and one explicitly supplied area. It classifies every integer-meter distance, calculates the corresponding tier amount and returns the maximum **once**, with a defensive Purbadhala ৳30 assertion. The 50-delivery input limit is a software bound inherited from the existing cart limit, not a confirmed rider capacity policy. Stable unique identifiers prevent duplicate entries; identifiers themselves do not verify assignment uniqueness. Synthetic tests cover both areas, examples, all boundaries, multiple riders, permutation, invalid IDs and inputs, and rejection when even one delivery exceeds 3 km.

This remains an unexported, unwired arithmetic draft, not a quote, order, or live cap enforcement. The input must represent **each rider's entire delivery**, not automatically each store or each store-to-destination leg. The existing local-stub matrix preview returns separate store-to-destination distances and cannot establish a multi-stop rider trip; it must not be used as proof of this rule's inputs. The owner subsequently chose first store → subsequent stores → customer, excluding the rider's approach; see `docs/186-cod-rider-itinerary-draft.md`. Actual multi-pickup itineraries, travel mode, provider and when distances/assignments become final still need an operational specification. The function neither verifies those inputs nor determines zone eligibility, customer location, fee/tax/discount completeness, cancellation behavior, rider pay, or how the single charge and product amounts are split for COD cash collection.

A live COD system still needs an authoritative server-side quote bound to recipient, area, actual rider delivery distances and complete cart; enforceable order-level cap across all applicable charges; durable allocation, finance and database invariants for multiple deliveries; security, identity, isolated infrastructure, and end-to-end testing. A routing and map provider may charge money and receive customer coordinates, so cannot be enabled without privacy/cost review. No production gate, hosted database, external provider, or deployment changed.
