# Cart response safety

The web BFF previously trusted any successful cart response. Missing fields, an unexpected market, malformed line data or invalid identifiers could crash the cart/checkout UI or be used to construct a downstream mutation path. The get-or-create read now checks the configured market, cart and line identifiers, safe positive version, active-quote identity, required render/mutation field types, nonnegative integer availability and unique line/variant identities. An unreadable response becomes the existing unavailable state. Cart mutations and quote creation already obtain the cart through this read, so they do not send a subsequent command when validation fails.

This is a structural check, not an ownership or price authorization boundary: the API must still enforce access and current prices. String pricing, currency and numeric quantity values that are structurally usable but semantically invalid remain visible to the existing summary, which reports problems and blocks checkout rather than disguising them. A 502 for unavailable cart data can conservatively appear as an uncertain mutation to the browser; this change does not establish durable mutation idempotency.

Local verification: 676 unit/component tests, typecheck and isolated production web build passed. Unit tests exercise valid/empty carts, malformed or wrong-market carts, duplicate IDs, bad availability and sellable types, semantic price/quantity issues, signed-out/network failures, and prevention of subsequent cart/quote commands. Chromium with a synthetic cart/session tested malformed and wrong-market responses and keyboard recovery on cart and checkout at 320, 390 and 1440 CSS pixels; selected Axe and overflow checks passed. No real cart service or identity provider was used.

This does not validate every API response, address cross-tab cart edits, guarantee price or stock, or implement payment or order placement. No Supabase connection, user database change or production deployment occurred.
