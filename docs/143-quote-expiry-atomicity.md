# Quote expiry atomicity and lock ordering

Migration `0073_quote_expiry_locking` changes the shared expiry function to process one atomic unit per transaction: either one whole quote or one standalone reservation. It obtains the quote lock before inventory, matching the checkout release and order-creation paths. Quote lines acquire inventory locks in variant-ID order. The internal reservation-close path also locks an associated quote before inventory. A quote already locked by another transaction is skipped, not processed under inventory locks.

A quote is eligible only when **all** of its reservations have reached their own expiry times. This can hold stock briefly beyond the quote's earliest expiry, but avoids an invalid partial closure and never expires a reservation early. The function rejects a quote with more than 50 items (the supported API cart limit). It compares eligible quote age with standalone reservation age to avoid always prioritizing one class. A locked or concurrently changed item can result in a zero-work tick; the next poll retries.

The worker and internal API repeat one-unit transactions up to a reservation budget, never hold one unit's inventory locks while acquiring another quote. The configured batch size is now a **soft** budget: one indivisible quote may return up to 50 expired reservations even when the budget is lower. Direct SQL calls process one unit, not a whole multi-unit batch. Worker errors log the failure and count any earlier committed units rather than reporting zero for the entire tick. Production needs monitoring, scheduling and throughput assessment; the worker remains opt-in.

## Verification and limitations

The original diagnostic was replaced with positive PostgreSQL tests. A two-line quote closes under budget one; actual release proceeds while expiry skips a held quote; two expiry workers race safely; subsequent release sees the expired state. Tests check both reservation states, inventory, movements and exactly one quote event. A separately timed fixture verifies an older standalone reservation can expire while a quote with staggered reservation deadlines remains wholly active. Existing standalone expiry integration tests and worker unit tests remain. These tests use disposable CI infrastructure; they do not establish every possible workload, deployment compatibility, throughput or production correctness. Direct privileged writers that bypass the supported lock ordering remain outside the API guarantee.

## Deployment boundary

No hosted migration or deployment was performed. Before any hosted rollout, review the shared database, back up and rehearse on an isolated environment, quiesce expiry workers and related checkout/order writers, apply the migration and matching application/worker code as one coordinated release, verify grants and state, then resume with monitoring. Running the new worker against the old function reintroduces the original failure. A rollback to the old function reintroduces both known defects and requires expiry to remain stopped until an independently reviewed recovery plan is in place. This document is not authorization to modify existing Supabase data.
