# Isolated pointer change history

Migration `0077_isolated_boundary_pointer_history` adds an owner-only, append-only structural record for each insert/update of the experimental pointer from `docs/167`. A pointer and its history row are written in the **same database transaction**. Each row records zone ID, pointer version, previous and new boundary IDs and a database wall-clock timestamp; it deliberately contains no recipient data. Version 1 has no previous boundary; later rows name distinct old and new boundaries. Primary and foreign keys preserve references. Failed history inserts abort pointer changes, and rollback removes both. Trigger-level guards reject ordinary direct history insertion and updates/deletes, including by the table owner; the owner can still disable or change database controls.

The migration takes an exclusive lock and refuses to proceed if any pointer already exists: it cannot truthfully manufacture earlier history. There is no automatic backfill or deletion. A real upgrade with pre-existing pointers requires an explicit separately reviewed baseline/retirement plan. FORCE RLS, an owner-only policy and revocation from PUBLIC/runtime/privileged apply to the new table and persist across `db-grants.sql` reruns.

Disposable tests cover creation, versioned changes, prior/new IDs, failed and concurrent updates, transaction rollback when history insertion is forced to fail, owner direct-write rejection, application-role denial, and the migration precondition against an existing pointer. This is a structural history, **not an authenticated approval audit**: it contains no actor, reason, request, geographic authorization or maker/checker evidence; wall-clock timestamps are not an ordering guarantee, and version is the per-zone order. Directly approved boundary inserts and privileged database-owner control remain unresolved. It does not activate a boundary, define deactivation, resolve overlaps, or connect the pointer to checkout or dispatch. No migration or data was applied to the user's hosted database; the shared Supabase project is not an isolated testing environment.
