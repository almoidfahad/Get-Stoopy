# Notification creation retries

The notification create endpoint previously returned the existing notification for any reuse of the same `(userId, commandKey)`, even when the message differed. Simultaneous identical calls could also both miss the lookup, with one then failing the unique index instead of replaying successfully.

Creation still requires the caller's own user ID and `notification.create`. It now takes a transaction-scoped advisory lock on a namespaced, canonical user ID plus command key before the lookup. A matching type, channel, subject, body and template ID returns the existing row with `duplicate: true`; a mismatch returns `409 NOTIFICATION_IDEMPOTENCY_CONFLICT`. Template UUIDs are compared case-insensitively via their normalized representation. Different users can independently use the same key. A successful first call continues to create one notification, attempt, audit and outbox event in a transaction. The lock is coordination, not authorization, and hash collisions only serialize unrelated commands.

The existing `payloadHash` is SHA-256 of the command key, not of message content. This change deliberately compares stored content instead of introducing a hash of potentially sensitive message text, and works with existing rows without a migration. It is not a tamper-proof snapshot: a privileged writer changing stored message fields can change what later comparisons see. Direct database writers also do not participate in the service's advisory lock. The response shape for a matching replay is unchanged; a different-content replay intentionally changes from success to conflict. This does not enable any live delivery provider or establish that arbitrary notification text is safe for production.

Local service mock tests check authorization ordering, lock-before-lookup, legacy rows, UUID case, changed fields and side effects. A native PostgreSQL 16.13 rehearsal ran the compiled service using synthetic tables and a small `pg` transaction adapter: it observed an advisory lock wait, one creation and one identical replay, rejection of changed content, and one each notification/attempt/audit/outbox. The local private-socket server was stopped. This is not the real Prisma/PostGIS/Redis integration suite. A repository integration test covering simultaneous requests, differing fields, other users and record counts has been added but remains unverified until GitHub Actions billing is resolved. Simultaneous requests alone do not prove observed blocking. No hosted database change or deployment was performed.
